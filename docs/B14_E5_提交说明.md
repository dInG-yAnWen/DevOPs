## 3. 实验过程和结果

|步骤/候选|构建预算|实际构建时间|构建结果|程序运行|
|---|---:|---:|---|---|
|初始 Dockerfile|600 秒|1.321 秒|Docker 退出 1；`make: not found`，RUN 内退出 127|不运行|
|error-driven 原始候选|240 秒|240.023 秒|`TIMED_OUT`，依赖下载未完成|未到达验证，不计成功|
|context-driven 原始候选|240 秒|240.003 秒|`TIMED_OUT`，依赖下载未完成|未到达验证，不计成功|
|context-mirror 环境适配候选|600 秒|125.429 秒|退出 0|同一 image ID，退出 0，精确输出 `hello E3\n`|

时间来自各次 `build/command.json` 的 UTC 起止时间。超时结果的 `exit_code=null`、`timed_out=true` 表示没有观察到正常完成的 Docker 退出码；驱动返回 2。初始故障是验收预期，驱动正确取证后返回 0。三种退出含义没有混用。

原始日志明确到达 `RUN make`，定位与提示来自这份实际日志。error-driven 提示包含故障 Dockerfile 和日志；context-driven 在相同输入上增加 README。两份回复均安装 `build-essential`，差别只有换行排版。按课堂续行/空白归一化后完全相同。

候选选择记录见 [decision.json](../e5/evidence/20261030-241880284-e5/decision.json)：

- **R1 去重：**两份原文分别保留，归一化后只有一个不同的依赖修复方案。
- **R2 多数规则：**未开展独立的多候选投票实验，不把两个提示的一致输出解释为额外统计证据。
- **R3 错误相关性：**两份候选都安装了提供 make 和 C 工具链的包，针对缺失命令提出直接修复。
- **R4 模型裁决：**不存在待裁决的不同修复方案，本次未再调用模型选优。

默认源可访问但下载较慢。error-driven 日志显示下载 10.2 MB 包索引耗时约 131 秒，随后开始下载 88.1 MB 安装包，在 240 秒预算内未完成。没有观察到 C 编译错误，不能把超时写成修复语义错误。

独立候选 `context-mirror` 将构建容器内软件源域名改为 `mirrors.aliyun.com`，增加 IPv4、2 次重试和 30 秒 HTTP 超时。保留原 FROM、安装包、源码、WORKDIR、COPY、`RUN make` 和 CMD，修改 diff 与父候选哈希均已保存。最终来源类型为 `ENVIRONMENT_ADAPTATION`，没有覆盖模型原文。

选择适配候选，是因为它完成了实际构建和程序验证。适配同时改变软件源、下载参数和预算，且两次原始候选构建有时间重叠；结果不支持镜像源的单因素加速结论，也不支持某类提示更优的结论。
