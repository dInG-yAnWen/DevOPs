B14 的 REPAIR 需要读取 A14 本轮的 MD-only Report，并把补丁交回 A14 动态复验。1.0 Report 可以表达 A14 的 `STATIC_INFERENCE` 发现。图、重检和镜像元数据的 1.0 内容 Schema 中，`source` 仍限定为 `MANUAL_FIXTURE`。

沿用 1.0 REPAIR 请求和 Report 的校验方式。课程任务 API 使用原有 `e11e12-1` 外层，登记图、重检和日志原件的路径与 SHA-256。统一 `trace_id`，各组件的生产 Job ID 分别记录。核对原件的仓库、提交、配置、生产者及候选补丁哈希。

候选在 C1 的独立检出上生成，从 Git 仓库根目录应用。REPAIR 请求的 `makefiles` 使用 A14 报告中的 `Makefile`，执行目录独立记录。修复前后均使用 C1，补丁 URI 和 SHA-256 标识候选工作树。复验失败时归档失败原因和已有证据。

直接升级契约需要双方共同更新 Schema、校验器、样例和调用方。首轮使用现有接口即可传递真实报告，并独立验证图和复验证据。

测试覆盖旧报告、人工来源、哈希不符、候选重检错绑、A14 失败记录、幂等冲突和回环 HTTP 交接。共同项目还在 WSL 中通过 A14 的实际检测和动态重检。
