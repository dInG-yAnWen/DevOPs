## 上机准备

在 Linux 云服务器上使用 B14 仓库，确认本地 Git 用户名是本人学号。已有 `data/integration-sample` 时直接复用。

```bash
python3 run_e11e12.py build

python3 run_e11e12.py prepare
python3 run_e11e12.py run --request data/integration-sample/e11-b.json --out work/e11-b-01

```

课程样例证据在对应 `work/` 目录。真实跨组运行在 `data/pair14/<轮次>/` 准备交接，使用新的幂等键和输出目录。A14 可通过 SSH 转发访问监听在服务器回环地址的 API。

1. **杨王旭**交付 DRAFT 的实际 `image_ref`、`configuration_id`、Job ID、Dockerfile、构建和验证日志及 Artifact 记录。保留初始失败和候选成功的日志，向 A14 提供下载位置与镜像仓库读取方式。A14 使用 `docker pull "$IMAGE_REF"` 并在检测时挂载对应的 C0 或 C1 检出目录。记录实际使用的 digest 和本地镜像 ID。
2. **A14**在同一配置和同一个 `trace_id` 下运行 C0 全量和 C1 增量，提供 `a_track.py` 输出的 `manifest.json` 和对应原件。通过清单读取实际图、声明图和独立的 1.0 MD-only Report（`md.json`），保留生产 Job ID 和 SHA-256。镜像 digest 和 `trace_id` 附在本轮执行记录上。
3. **丁彦文**将收到的原文件放到这一轮的交接目录，按下表填写 `handoff.json`。其中记录可读取文件和 SHA-256，文件路径相对交接目录。A14 的图、真实重检和镜像原始元数据沿用真实来源，不使用 1.0 内的 `MANUAL_FIXTURE` 字段。
4. **徐梓航**核对候选范围，使用同一个镜像运行构建和行为验证。A14 使用同一份候选做动态重检。保存候选、原始日志和发现；B14 根据退出码和剩余 MD 作出接受判定。

## 输入文件和回传记录

| `handoff.json` 字段 | 内容 |
| --- | --- |
| `repair_request` | 原 1.0 REPAIR 请求。仓库指向 C1，`build.working_directory` 为项目子目录，`environment` 使用 DRAFT 的 digest 和配置，`md_report_uri` 使用 A14 发布的 URI。 |
| `draft` | `job_id`、`commit`、`trace_id`、`status`、`configuration_id`、`image_ref`，另含 `build_exit_code`、`verify_exit_code` 和 `dockerfile`、`build_log`、`verify_log` 三项文件引用。每项文件引用形如 `{"path":"文件名","artifact":{...}}`，其中 `artifact` 是 1.0 Artifact。 |
| `full_check` | 同样六个阶段字段，commit 为 C0。加 `actual_graph`、`declared_graph`，引用形如 `{"path":"文件名","sha256":"..."}`。 |
| `incremental_check` | 同样六个阶段字段，commit 为 C1。加 `base_commit`、实际图和声明图引用，及 `md_report`。MD 报告引用使用 `path` 加 1.0 Artifact，类型为 `ERROR_REPORT`。 |
| `recheck_file` | 回传 JSON 的相对文件名，例如 `recheck-return.json`。 |

API 提交正文结构如下。将轮次、幂等键和交接文件的实际 SHA-256 填入后，用 `curl -fsS -H 'Content-Type: application/json' --data-binary @submit.json http://127.0.0.1:8080/v1/jobs` 提交。

```json
{
  "idempotency_key": "pair14-e12-01",
  "input": {
    "mode": "e12",
    "repo": "/course/data/a14",
    "base": "4445e4be50af6683b75017e7fa65c4f8212ea80e",
    "target": "37fcadb1eced8d2504b1d5e0bd96f3b8091568b1",
    "handoff": "/course/data/pair14/01/handoff.json",
    "handoff_sha256": "<以 sha256sum 实际计算>"
  }
}
```

轮询 `GET /v1/jobs/<job_id>`。候选生成后，通过 `/v1/jobs/<job_id>/files/candidate-manifest.json` 和清单里的下载路径读取补丁。对比 `X-Content-SHA256`、清单和下载文件三者的哈希。补丁从 **C1 Git 仓库根目录**应用，先运行 `git apply --index --check /绝对路径/candidate.patch`，再运行 `git apply --index /绝对路径/candidate.patch`。候选工作树的源码版本仍记录为 C1。

在 A14 的执行环境中，使用同一份 MD 报告和候选清单运行复验。环境变量均取本轮实际值，路径指向执行环境内可见的文件。

```bash
python3 labs/e11e12/recheck.py \
  --repo "$A14_REPO" --project-path e3/fixtures/commits/project \
  --target 37fcadb1eced8d2504b1d5e0bd96f3b8091568b1 \
  --patch "$PATCH_FILE" --patch-uri "$PATCH_URI" --patch-sha256 "$PATCH_SHA256" \
  --md-report "$MD_REPORT" --repository-url https://github.com/oVLVo11/DevOps_A14.git \
  --configuration-id "$CONFIGURATION_ID" --expected-output 12 --out "$RECHECK_OUT"
```

回传清单包含同样六个阶段字段，`job_id` 取 A14 原始 `recheck.json` 的 `producer_job_id`。另填 `repository_url`、`patch_uri`、`patch_sha256`、`build_exit_code`、`verify_exit_code`。用路径和哈希引用 `a14_result`（原始 `recheck.json`）、`findings`（`full-recheck/findings.json`）、`build_log` 与 `verify_log`。先放原始文件，再将完整回传清单原子重命名为约定文件名。API 等待窗口采用 REPAIR 请求的 `execution.timeout_seconds`。结果从 `GET /v1/jobs/<job_id>/artifacts` 获取。

若 A14 的入口生成 `failure.json`，回传清单使用 `status: FAILED` 和 `a14_failure` 文件引用，并附上已产生的日志。最小拒绝复现是故意传入错误补丁哈希，复验应在应用前报 `ARTIFACT_HASH_MISMATCH`。有效候选在隔离副本应用。若构建或验证失败，保留该副本的证据，保留原 C1 检出用于下一轮。

- 同键同输入返回原 Job，改动输入返回 HTTP 409。

- 补丁只改目标 Makefile。保存构建、输出 12、修改头文件后增量输出 15、A14 重检无 MD 的证据。RD 按实际发现记录。
