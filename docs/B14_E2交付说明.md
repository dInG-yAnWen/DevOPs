## 1. 交付结论与边界

本包已完成 B14 可独立完成的 E2 交付内容：需求边界、四类统一任务契约、请求/受理/结果/异常/产物样例、离线校验器、Backlog、ADR 与设计过程记录。主文件可作为 E2 材料入口，机器可校验文件保留在仓库中。

按课件，B 组负责 DRAFT 与 MDFixer 两项。本包定义 DRAFT 和 REPAIR，并提供 A14 已接受的 FULL_CHECK、INCREMENTAL_CHECK 消费契约，覆盖四类任务的交接关系。A14 负责两类检测服务的实现。

E2 使用人工构造的 C/Make 协议样例，执行结果标为模拟数据，用于验证字段、状态和产物绑定。契约版本已发布，离线校验通过；成员贡献审阅与课程平台提交记录仍待补齐。真实实验结果分别记录在 E3、E4 材料中。

## 3. E2 1.0 约定与新增记录

1. 沿用原 DRAFT 端点、1.0 版本、六种状态、默认 3 次尝试和 1800 秒时限。
2. 四服务共享 Job 外层，通过 job_type 选择专有 input/output。成功和异常样例均可验证。
3. MD/RD 为 ERROR_REPORT 中的业务发现，正常检测为 SUCCEEDED。DRAFT 搜索失败与所有修复候选无效为 FAILED + GOAL_UNMET；系统异常为 SYSTEM。
4. 采用 artifact:// 逻辑引用、manifest 本地映射与 sha256；image_ref 独立锁定镜像 digest。
5. REPAIR 消费同仓库、同 commit、同配置且仅含 MD 的报告。接受 patch 必须通过构建、测试和针对该 patch 的重检。
6. 历史构建命令由 A14 内部按 repository_url + base_commit + configuration_id 保存，baseline.build_commands_uri 留作后续接口评审。
7. E2 保留人工协议样例。双方 E3 样本、固定版本与 E4 环境资料见 [E3/E4 交接记录](collaboration/E3E4_交接记录_20261008.md)。

确认依据及本次交接结果见 [协作确认与交接记录](collaboration/交接确认.md)，其中保留 A14 回复原始字节与来源包 SHA-256。

## 4. 交接演示顺序

1. 阅读 `draft_request.json` 与 `draft_result.json`，用解析命令读取 Dockerfile 和 image.json，注意 image.json 的 available=false 表示本地协议样例。
2. 阅读 `full_request.json`：复用 DRAFT 环境与相同配置。查看全量结果中的图和 findings.json，其中 MD 与 RD 并存而 status=SUCCEEDED。
3. 阅读 `incremental_request.json`：当前提交为示例 C1，baseline 绑定 C0、同仓库和同配置。结果新增/消除集合由两次报告对比得出。
4. 阅读 `repair_request.json`：消费 A14 样例中单独过滤的 md.json；查看 fix.patch、声明风格及三项候选验证。
5. 对比 `draft_goal_unmet.json`、`draft_failed.json` 与 `repair_goal_unmet.json`，解释目标未达成、系统失败和候选拒绝的区别。
6. 运行完整套件，演示未知 job_type、缺 baseline、混入 RD 被拒绝。

## 5. 复现命令

```sh
python validator/validate.py --suite
python validator/validate.py contracts/examples/valid/draft_request.json
python validator/validate.py contracts/examples/invalid/missing_baseline.json
python validator/validate.py --read-artifact artifact://b14-draft/job-draft01/Dockerfile
```

第三条预期退出码为 1，其他为 0。环境无 `python` 命令时使用可用 Python 3.10+ 的解释器路径。校验无需网络、Docker 或 LLM 额度。
